# Orchestration Engine

This file defines the core task allocation and routing rules for the Chief Architect.

## Agent Spec Format

Every agent in this orchestrator is defined with a **YAML spec block** at the top of its `.md` file. The spec defines the agent's identity, capabilities, and constraints in a structured format:

```yaml
agent: AgentName              # Unique identifier
tier: 0|1|2                   # 0 = Master Orchestrator, 1 = Team Leads/Management, 2 = Specialist Agents
persona:
  role: "..."                 # Job title
  goal: "..."                 # Primary objective
  backstory: "..."            # Character and expertise
model: claude-opus-4-6        # LLM model to use
tools: [...]                  # Available capabilities
inputs: [...]                 # What this agent receives
outputs: [...]                # What this agent produces
constraints: [...]            # Hard rules this agent must follow
reports_to: AgentName         # Who this agent reports to
delegates_to: [...]           # Who this agent can assign work to (leads only)
```

### Tier Hierarchy
```
Tier 0: MasterOrchestrator (CLAUDE.md)
  ├── Tier 1: Management (ProjectManager, BusinessAnalyst, TechLead, QALead, DevOpsEngineer)
  ├── Tier 1: APITeamLead → Tier 2: BackendArchitect, DatabaseEngineer, AuthSecurity, IntegrationSpecialist, APITester
  └── Tier 1: AppTeamLead → Tier 2: UIArchitect, FrontendEngineer, StylingSpecialist, UXEngineer, AppTester
```

When launching a subagent, include the relevant YAML spec in the prompt so the agent knows its identity, constraints, and expected outputs.

## Execution Model

**All application code is generated by Task subagents, not by the orchestrator directly.**

The orchestrator uses the **Task tool** to launch subagents:
- `subagent_type: "general-purpose"` for all code generation
- **Multiple Task calls in ONE message = parallel execution**
- Each subagent gets ONE agent role and ONE work item
- Use `model: "haiku"` for simple tasks, `model: "sonnet"` for medium tasks, default (opus) for complex tasks
- Use `run_in_background: true` for non-blocking tasks (tests, docs)
- See `.orchestrator/workflow.md` for the subagent prompt template and wave execution protocol

### Progress Tracking

The orchestrator MUST maintain a **TodoWrite** list throughout execution:
- Create the full task list during decomposition (Phase 3)
- Mark tasks `in_progress` BEFORE launching subagents
- Mark tasks `completed` IMMEDIATELY when subagents return successfully
- Add new tasks when discovered during execution
- Never batch completions — update in real-time

### Token Budget

| Phase | Est. Tokens | Model |
|---|---|---|
| Discovery + Contract (Phase 1-3) | ~5,000 | Main context |
| Simple subagent (schema, types) | ~10,000 | Haiku |
| Medium subagent (CRUD module) | ~25,000 | Sonnet |
| Complex subagent (auth, plugins) | ~50,000 | Opus |
| Validation + Quality Gate | ~8,000 | Main context |

Optimize prompts: inline small contracts, reference large docs, summarize prior outputs.

## Task Classification

Every incoming request must be classified before allocation:

### `[API]` — Backend Only
Route entirely to the API Team when the task involves:
- REST/GraphQL endpoint creation or modification
- Database schema, migrations, queries, or seed data
- Authentication, authorization, middleware
- Server-side validation and business logic
- Third-party service integrations (payment, email, storage)
- Backend environment config, server setup

### `[APP]` — Frontend Only
Route entirely to the App Team when the task involves:
- UI component creation or modification
- Page layouts, routing, navigation
- State management (stores, context, reducers)
- Styling, theming, responsive design
- Client-side form handling and validation
- Frontend-only features (animations, transitions, local storage)

### `[FULL-STACK]` — Both Teams
Requires coordination between both teams when:
- A new feature needs both an API endpoint AND a UI
- Data flows from server to client (new data model → API → frontend)
- Authentication/authorization that affects both server and client
- Any task where frontend depends on a backend contract

## Task Decomposition Rules

### Work Item Structure
```
ID:            {TEAM}-{NUMBER}  (e.g., API-1, APP-3)
Team:          api-team | app-team
Agent:         Which agent handles this (see team orchestrator files)
Title:         Short description
Description:   Detailed requirements
Dependencies:  [list of work item IDs that must complete first]
Deliverables:  [list of files/artifacts this produces]
Priority:      critical | high | medium | low
```

### Dependency Rules
1. **Shared types/interfaces** must be created before any implementation that uses them
2. **API endpoints** should be defined (at minimum the contract/types) before frontend calls them
3. **Database schema** must be created before API logic that queries it
4. **Auth middleware** must exist before protected routes use it
5. Work items with **no dependencies** can execute in parallel immediately
6. **Shared contract** must be defined (Wave 0) before EITHER team starts implementation
7. **Shared utilities** (response helpers, auth headers, base components) must exist before feature work
8. **Tests** can only run after the code they test is complete

### Decomposition Heuristics

**By Feature Type:**

| Project Type | Decomposition Pattern | Model Hint |
|---|---|---|
| **CRUD Feature** | Schema → Zod → API module (3 files) → FE types/service/hooks → UI components → Page → Route → Tests | Haiku for schema/zod, Sonnet for modules/components |
| **UI-Only Feature** | Types → Component hierarchy → Styling → State management → Tests | Sonnet for components |
| **Auth System** | DB schema → Auth controller → JWT middleware → RBAC middleware → Login/register pages → Auth context → Protected routes → Tests | Opus for auth logic |
| **Integration** | Service client wrapper → Webhook handler → Error translation → Env config → Integration tests | Sonnet for wrappers |
| **Refactoring** | Identify files → Plan changes → Execute per-module → Update imports → Verify tests | Sonnet for refactors |
| **Real-Time Feature** | Socket.IO server setup → Event handlers → Client socket hook → UI updates → Tests | Opus for socket logic |
| **File Upload** | Upload middleware → Storage config → Upload endpoint → FE dropzone → Preview component | Sonnet |
| **Dashboard/Analytics** | Data aggregation endpoint → Chart components → Dashboard page → Real-time updates | Sonnet for charts |
| **Plugin System** | Plugin interface → Loader/registry → Lifecycle hooks → Plugin API → Management UI | Opus for plugin arch |
| **Infrastructure** | Project scaffold → Config files → Build scripts → Environment setup → CI/CD | Haiku for configs |

**Sizing Rules:**
- Keep work items **small enough** to be done in one focused pass (one agent, one task)
- Keep work items **large enough** to be meaningful (don't create a task for every single line)
- If a work item touches more than **5 files**, consider splitting it
- If a work item requires more than **2 agent specialties**, split by specialty
- Assign `model: "haiku"` to simple schema/type/config tasks to save tokens

## Agent Routing Table

| Task Pattern | Team | Agent |
|---|---|---|
| API design, routes, controllers | api-team | backend-architect |
| Database models, schemas, migrations | api-team | database-engineer |
| Auth, JWT, sessions, permissions | api-team | auth-security |
| External API calls, webhooks, services | api-team | integration |
| API test writing, endpoint validation | api-team | api-tester |
| Component architecture, design system | app-team | ui-architect |
| Feature components, pages, state logic | app-team | frontend-engineer |
| CSS, layouts, responsive, animations | app-team | styling-specialist |
| Accessibility, performance, UX patterns | app-team | ux-engineer |
| Frontend tests, E2E, component tests | app-team | app-tester |

### Routing Decision Logic

When a work item could match multiple agents, use these priority rules:

1. **Most specific agent wins**: "Create JWT middleware" → AuthSecurity (not BackendArchitect)
2. **Data-layer work → DatabaseEngineer**: schema, relations, seeds, queries
3. **API logic → BackendArchitect**: endpoints, controllers, routing, Zod validation
4. **Feature with data → FrontendEngineer**: hooks, state, data fetching, pages
5. **Pure visual → StylingSpecialist**: only appearance, not behavior
6. **Complex component design → UIArchitect**: component hierarchy or design system
7. **Always separate testing**: don't bundle test writing with implementation — use APITester or AppTester
8. **Simple tasks get cheaper models**: schema/type tasks → `model: "haiku"`, CRUD → `model: "sonnet"`

## Cross-Team Coordination

When a `[FULL-STACK]` task requires both teams:

### Ownership

| Responsibility | Owner |
|---|---|
| Define the shared contract (types, endpoints, response shapes) | **Chief Architect** (main context, Wave 0) |
| API implementation against the contract | **API Team** (BackendArchitect, DatabaseEngineer, etc.) |
| Frontend implementation against the contract | **App Team** (FrontendEngineer, UIArchitect, etc.) |
| Integration verification | **Chief Architect** (main context, Wave 3) |
| Conflict resolution | **Chief Architect** — the contract is the source of truth |

### Coordination Timeline

```
Wave 0: Chief Architect defines the contract (main context)
         ↓
Wave 1: API Team + App Team work in PARALLEL on independent items
         (schema, types, services — no cross-dependencies)
         ↓
Wave 2: API Team builds endpoints, App Team builds UI
         (both teams work against the contract — still parallel)
         ↓
Wave 3: Chief Architect verifies integration
         (reads both sides, fixes mismatches against the contract)
         ↓
Wave 4: Both teams write tests in PARALLEL
```

### Conflict Resolution

1. **Contract is the source of truth** — if teams disagree, check the contract
2. **If API deviates** → fix the API side (don't change the contract for convenience)
3. **If App deviates** → fix the App side
4. **If the contract is wrong** → update contract AND fix both sides
5. **Never modify both sides to "meet in the middle"** — one source of truth
6. **If it fails twice** → escalate to the user with both outputs

## Error Handling During Orchestration

- If an agent's work fails → analyze the error, fix it, and retry that work item only
- If a dependency is blocked → flag it, work on independent items, return to blocked item later
- If teams produce incompatible code → the Architect mediates and aligns the contract
- If scope grows unexpectedly → pause, re-decompose, and inform the user
